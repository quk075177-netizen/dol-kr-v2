# post(조사) 시스템 설계

기준일: 2026-08-08
상태: 설계 (구현 전)

## 배경

파일럿(P1)에서 **LLM이 조사 마커를 자동 생성**하는 것을 확인했다:

```text
원문: <<npc>> 패들로 당신의 <<bodypart>> 치려고 하지만
번역: __DOLKR_P000051__이(가) __DOLKR_P000052__ 당신의 __DOLKR_P000053__을(를)
      __DOLKR_P000054__으로(로) 치려고 하지만
```

- 원문에는 조사가 없다. 매크로 출력(런타임 값) 뒤의 조사를 LLM이
  `이(가)` / `을(를)` / `으로(로)` **쌍 표기**로 생성했다.
- 받침을 모르는 런타임 값이므로 쌍으로 남긴 것이다 — KO HTML의 `【 】`
  마커(ko-marker-analysis.md)와 같은 원리.
- **이 마커는 게임에 그대로 표시되면 안 된다.** 받침 판정(post) + 치환이
  필요하다.

LLM은 조사 **종류 선택**(주어 이/가 vs 목적어 을/를 vs 도구 으로/로)을
문맥으로 정확히 처리한다 (P1 검증). 우리가 할 일은:
1. LLM이 생성한 비정형 표기(`이(가)`, `(이)가` 등)를 **표준 post 마커**로
   정규화
2. 표준 마커를 받침 판정(getPostNum)으로 **확정 조사로 치환** (정적/동적)

## 조사 종류 (26개 × 3형태 — dol-kr trPostsList 기준)

| 조사 | 받침O(0) | 받침X(1) | ㄹ받침(2) |
|---|---|---|---|
| 은/는 | 은 | 는 | 은 |
| 이/가 | 이 | 가 | 이 |
| 을/를 | 을 | 를 | 을 |
| 과/와 | 과 | 와 | 과 |
| 으로/로 | 으로 | 로 | 로 |
| 이다 | 이다 | 다 | 이다 |
| 이었/였 | 이었 | 였 | 이었 |
| (기타 19개) | ... | ... | ... |

## getPostNum 규칙 (확정, 재사용)

```python
def get_post_num(text: str) -> int | None:
    """0=받침O, 1=받침X, 2=ㄹ받침, None=미정(라틴/기호/빈값)"""
    if not text:
        return None
    ch = text[-1]
    code = ord(ch)
    if 0xAC00 <= code <= 0xD7A3:          # 한글
        jong = (code - 0xAC00) % 28
        return 0 if jong != 0 and jong != 8 else (2 if jong == 8 else 1)
    if ch.isdigit():                       # 숫자
        return [0, 2, 1, 0, 1, 1, 0, 2, 2, 0][int(ch)]
    return None                            # 라틴/기호
```

## LLM 출력 마커 정규화

LLM이 생성하는 비정형 표기를 표준 마커로 정규화한다. 실제 파일럿에서
관찰된 형태:

| 관찰 표기 | 표준 마커 |
|---|---|
| `이(가)` | `{{post:이가}}` |
| `을(를)` | `{{post:을를}}` |
| `으로(로)` | `{{post:으로로}}` |
| `은(는)` | `{{post:은는}}` |
| `와(과)` | `{{post:와과}}` |
| `이네(이구나)` | `{{post:이었였}}` + 어미 |

정규화 규칙:

1. **파일럿 번역 후처리**에서 정규식으로 `이(가)`→`{{post:이가}}` 변환
   (한국어 조사 쌍 목록: 은(는)/이(가)/을(를)/과(와)/으로(로)/이었(였)/...)
2. **프롬프트 지시**로 LLM이 처음부터 표준 마커를 출력하게 유도:
   "받침이 불확실한 값 뒤의 조사는 `{{post:이가}}` 형태로 남겨라"
   → 비정형 표기 의존도 감소
3. **3-match 재사용**: 기존 KO의 `【 】` 마커 → `{{post:...}}`로 일괄 변환
   (표준화)

## 치환 (정적/동적)

### 정적 치환 (번역 빌드 타임)

마커 앞 값이 **고정 문자열**(받침 확정 가능)이면:

```text
"오션 브리즈 카페{{post:은는}}" → "오션 브리즈 카페는"  (포 받침X)
"빵{{post:을를}}"              → "빵을"               (ㅇ 받침O)
```

판정: 마커 앞 텍스트에 런타임 토큰(`$`, `_`, `<<`, `` ` ``)이 없으면 정적.
받침이 None(라틴/기호)이면 기본 받침X(1)로 처리 (ko-marker 규칙).

### 동적 치환 (게임 런타임)

마커 앞 값이 **런타임 출력**이면 게임 런타임에서 치환:

```twee
<<set $_name to "Robin">>
$_name{{post:이가}} 말했다
```

- 런타임 particle helper: `post_eval(value, "이가")` → 받침 판정 후 조사 반환
- SugarCube 매크로로 구현 (dol-kr EasyPost 참고, eval 없이 Macro.add 직접)
- **3-match의 91.8% 마커가 이 경우** (런타임 값 앞)

## glossary 연동

`research/data/glossary.yml`의 `(slot, key) → display_ko + post`:

- 의류명 삽입 시 `display_ko` + `post`로 조사 결정
- 예: `<<upperwear "sundress">>` → "선드레스" (post 1) → "선드레스를"
- glossary의 post가 정본 — 표시명 변경 시 재계산 필요 (이미 compute_post.py)

## 데이터 흐름

```text
[번역 후처리]
LLM 출력 → 마커 정규화(이(가)→{{post:이가}}) → 정적 치환(빌드 타임)
                                            └─ 동적 마커 잔존 → 게임 런타임 치환

[3-match 재사용]
KO body → 【 】→ {{post:...}} 일괄 변환 → 동일 경로
```

## 구현 순서

### PO1. 마커 정규화 + 정적 치환 모듈

`translation/post.py` (번역 파이프라인 후처리):

- `normalize_markers(text)`: `이(가)`/`【이가】` → `{{post:이가}}`
- `resolve_static(text)`: 마커 앞이 고정 문자열이면 조사 확정
- `get_post_num(text)`: 받침 판정
- 유닛 테스트: 조사별 받침O/X/ㄹ 3형태, 숫자 끝, 라틴(None)

완료 기준:

- 파일럿 번역 결과에서 `이(가)` 계열 마커 0개 잔존 (정적 처리분)
- `{{post:...}}` 잔존은 런타임 대상으로 명시

### PO2. 런타임 particle helper (게임 사이드, 별도 범위)

SugarCube 매크로 (dol-kr EasyPost 참고, eval 제거):

- `<<postEval value marker>>` — 받침 판정 → 조사
- 3-match 재사용 시 이 매크로가 필요

이 단계는 게임 조립 범위이므로 별도 문서로 분리한다.

### PO3. 3-match 재사용 파이프라인

`translation/reuse.py`:

- triple-match JSONL 로드 → KO body 마커 변환 → 표준 번역 유닛으로 승격
- 마커 없는 44%부터, 마커 있는 56%는 PO2 후

## 완료 기준 (전체)

- LLM 출력의 비정형 조사 표기가 전부 `{{post:...}}`로 정규화됨
- 정적 치환: 받침 확정 가능한 모든 마커가 조사로 변환
- 파일럿 재실행 시 전투 passage 번역에 `이(가)` 잔존 0
- 3-match 마커 없는 44% passage가 번역 유닛으로 승격 가능

## 알려진 한계 (P1 검증 결과)

1. **LLM이 마커 없이 조사를 확정하는 경우** (unit 3):
   ```text
   __DOLKR_P000031__가 패들로 당신의 __DOLKR_P000032__를 때리려 하지만
   ```
   - `이(가)` 쌍이 아니라 `가`로 **단일 확정**한 경우다. 받침을 추측한 것.
   - 이건 정규화로 잡을 수 없다. **프롬프트 지시**로 해결:
     "매크로 placeholder(런타임 값) 뒤의 조사는 반드시 `{{post:...}}` 형태로
     남기고, 받침을 추측해 조사를 확정하지 마라."
   - placeholder가 아닌 고정 텍스트 뒤의 조사는 LLM이 확정해도 무방
     (받침이 원문에 있으므로).
2. **placeholder 밀집 유닛의 placeholder 드롭**: 재시도 상한 3회 + 재시도
   프롬프트에 placeholder 수 명시로 대응 (P1에서 1건 실패 → 대응 적용).
3. **중복 마커 `으{{post:으로로}}`**: normalize가 `으로(로)`를 매치할 때
   `으`가 남는 경우가 있다. ADHOC 패턴에서 `으로(로)`는 `으`를 소비하도록
   정규식 보강 필요 (현재: `[으로로]\([으로로]\)` → `으`+`로(로)`가
   분리 매치됨). 표준 마커 `으{{post:으로로}}`는 런타임에서 `으`+`로`로
   처리할 수 있으나, 빌드 타임에 `으` 흡수를 권장.
